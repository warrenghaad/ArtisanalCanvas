# Interactive Geometry Research Engine for ArtisanalCanvas

## Executive summary

The most robust architecture for your Geometry Research Engine is a **React + TypeScript front end** anchored by **React Three Fiber on top of Three.js** for spatial rendering, **React Flow** for editable ontology graphs, a **FastAPI** Python backend for the curriculum/geometry engine, **Neo4j with the official Neo4j Python driver** for persistent graph storage, **NetworkX** for fast in-memory graph analytics, and **Bokeh server** for statistics panels and linked Python callbacks. That combination best matches your requirements: pasted-text intake, geometry keyword parsing, 2D/3D visualization, sweep/failure/residue animation, graph-node ontology, and Python-native analytics. React Three Fiber is a React renderer for Three.js and is built for declarative, state-driven, interactive scenes; React Flow exposes nodes, edges, change handlers, viewport utilities, custom nodes, and save/restore workflows; FastAPI is explicitly designed for typed, high-performance API work with automatic OpenAPI; Bokeh server is designed for interactive web apps connected to Python running on a server. citeturn45view0turn48view0turn37view1turn37view2turn53view0turn39view0turn39view1turn55view0turn59view0

For your **geometry engine**, the best Python-side toolkit is a layered one rather than a single monolith: **SciPy** for numerical math, interpolation, and scientific computation; **SymPy** for symbolic relationships, transformation rules, mechanics, vectors, and equation solving; **trimesh** for mesh loading/manipulation/analysis and watertight geometric operations; and **PyBullet** when you want rigid-body failure previews, contact behavior, or quick physical plausibility checks for “problem envelope” prototypes. citeturn56view0turn56view1turn57view0turn57view2turn57view3

For **image generation**, the strongest pattern is to expose two backends. Use **OpenAI’s Images API / Responses API** for chat-native, iterative image generation and editing, especially when the visual ideation is part of the same conversational workflow as your curriculum prompt. Use **Stability AI / Stable Diffusion APIs** when you want Stable Diffusion-family models, editing/upscaling/control endpoints, or self-hosted / enterprise-style deployment options. OpenAI explicitly differentiates single-prompt image generation via the Image API from multi-turn image editing via the Responses API; Stability AI explicitly offers API integration, editing services, and self-hosted licensing paths for its image family. citeturn29view0turn29view1turn29view2turn34view0

The main recommendation I would **not** follow is building the persisted graph layer around **py2neo**. Its own handbook is marked **EOL** and explicitly recommends the official Neo4j drivers instead. For your use case, that matters because your ontology is not a toy graph: it needs durable node and edge properties for primitives, profiles, failure envelopes, residue filters, tag families, and invention composites. citeturn60view0turn59view0

One important modeling implication from your own curriculum taxonomy is that the graph should preserve **separate tag families** rather than flattening everything into generic labels. In your Day A / Day B approach, metaphor, conceptual math, engineering/technology, and STEM classification are distinct conceptual axes, so the data model should treat them as separate, queryable first-class entities and relationships, not a single comma-separated tag field. That is especially important if you want to represent inventions as true **GE-Convergence composites** rather than as static objects. fileciteturn0file0 fileciteturn0file1

## Recommended architecture

The cleanest implementation is a **shared-state dual workspace**: a curriculum/chat workspace on the left and a geometry/graph workspace on the right, both driven by a single canonical entity store. React Three Fiber handles the 3D scene; React Flow handles node editors and graph topology; FastAPI exposes parser, geometry, ontology, analytics, and image-generation endpoints; Neo4j persists the graph; NetworkX provides light analytics and export utilities; Bokeh runs the dashboard surface. This pattern is a natural fit because R3F scenes are driven by React state, React Flow is designed around node/edge state and change handlers, FastAPI is standards-based for typed APIs, and Bokeh server is explicitly designed for Python-backed interactivity. citeturn48view0turn40view0turn37view2turn53view0turn39view0turn39view1

A good runtime split is this:

- **Browser responsibilities**: viewport interaction, drag/drop, live graph editing, playback of sweep animations, residue overlays, selection/highlighting, lightweight keyword previews.
- **Python responsibilities**: parse curriculum text into candidate primitives/profiles, compute sweeps and failure envelopes, calculate residue suggestions, run graph analytics, serialize reusable invention schemas, and generate dashboard feeds. This division lets the browser stay responsive while keeping the geometric rules reproducible in Python. The Bokeh docs are especially relevant here, because Bokeh server mode is built specifically for browser UIs whose interactivity is connected back to Python callbacks and server-side state. citeturn39view0turn39view1turn53view0

The most important front-end synchronization rule is: **every visible thing should have a stable graph ID**. A primitive in the 3D stage, the matching React Flow node, the inspector pane, the analytics panel row, and the Neo4j node should all share the same canonical ID. React Flow already assumes ID-based node and edge management; React Three Fiber already assumes React-state-driven rendering; putting both behind one entity store makes cross-highlighting and cross-editing straightforward. citeturn45view0turn48view0turn37view2

## Stack recommendation and library comparison

### Recommended stack

The recommended production stack is:

- **Frontend shell**: React + TypeScript, integrated into ArtisanalCanvas as a new workspace or route.
- **3D engine**: Three.js + React Three Fiber. Add the R3F ecosystem selectively, not all at once.
- **Ontology editor**: React Flow.
- **Backend**: FastAPI.
- **Graph persistence**: Neo4j with the **official Neo4j Python driver**.
- **Graph analytics**: NetworkX.
- **Python geometry layer**: SciPy + SymPy + trimesh + optional PyBullet.
- **Dashboards**: Bokeh server.
- **Image generation**: OpenAI Images / Responses plus Stability AI as an optional second provider. citeturn44view0turn48view0turn37view1turn53view0turn59view0turn55view0turn56view0turn56view1turn57view0turn57view2turn39view0turn29view1turn29view2turn34view0

Cables.gl is excellent for rapid visual prototyping, node-based interactive graphics, model loading, shaders, and exporting, but it overlaps with your planned React Flow ontology layer rather than fitting neatly underneath it. ## Data model and interface design

Your data model should store **ontology first, visualization second**. In other words, the engine does not primarily store meshes; it stores **semantic geometry entities** that can be rendered as meshes. That matters because a single “line” may appear as a 2D stroke, a 3D rod, a rotational axis, or a contribution edge in an invention composite. If you encode only the rendered object, you lose the conceptual meaning you care about. fileciteturn0file0 fileciteturn0file1

A good ontology backbone is:

- **Primitive**: Point, Line, Plane, Sphere, Tetrahedron, Cube, Arc, Spiral, Triangle, etc.
- **Profile**: a constrained behavior of a primitive, such as axial spin, hinge, linear drift, in-plane rotation.
- **ProblemEnvelope**: the spatial signature of failure, such as conical wobble, buckling, slippage, torque twist.
- **ResidueFilter**: the inverse-fit geometry that stabilizes or complements the failure.
- **Invention**: a composite / GE-Convergence node, not a flat object record.
- **Tag**: GEpHR, GEK, GE-Tt, GE-Te, GE-Stem, GEU-motif, etc., kept as family-aware tags.
- **Observation**: source text span, curriculum excerpt, historical note, image prompt, or learner annotation.
- **RenderSpec**: camera presets, material styles, sweep animation config, overlay layers. citeturn59view0turn55view0 fileciteturn0file0 fileciteturn0file1

That model lets an invention remain a **convergence point**. Instead of “wheel” or “spindle” being only an object, it becomes a node whose incoming edges preserve which primitives, profiles, residues, and metaphoric tags participated in its formation. That directly addresses your concern that inventions are composites of geometric elements and should remain legible as such.

## Code snippets and example artifacts

### React Three Fiber scene for primitives and sweep animation

React Three Fiber is a good fit here because it renders ordinary Three.js constructs declaratively and gives you frame-level control through `useFrame`. citeturn45view0turn48view0

```tsx
import React, { useMemo, useRef } from 'react';
import { Canvas, useFrame } from '@react-three/fiber';
import * as THREE from 'three';

type PrimitiveKind = 'point' | 'line' | 'plane';

type PrimitiveProps = {
  kind: PrimitiveKind;
  position?: [number, number, number];
  rotation?: [number, number, number];
  length?: number;
  size?: number;
};

function Primitive({ kind, position = [0, 0, 0], rotation = [0, 0, 0], length = 2, size = 1 }: PrimitiveProps) {
  if (kind === 'point') {
    // Render a visible marker for a 0D point
    return (
      <mesh position={position}>
        <sphereGeometry args={[0.06, 24, 24]} />
        <meshStandardMaterial />
      </mesh>
    );
  }

  if (kind === 'line') {
    // Represent a 1D line as a thin cylinder aligned to X
    return (
      <mesh position={position} rotation={rotation}>
        <cylinderGeometry args={[0.02, 0.02, length, 16]} />
        <meshStandardMaterial />
      </mesh>
    );
  }

  // Represent a 2D plane as a very thin box so it reads in 3D
  return (
    <mesh position={position} rotation={rotation}>
      <boxGeometry args={[size, size, 0.02]} />
      <meshStandardMaterial />
    </mesh>
  );
}

function SweepGhost({
  source = [0, 0, 0],
  target = [2, 0, 0],
  duration = 2
}: {
  source?: [number, number, number];
  target?: [number, number, number];
  duration?: number;
}) {
  const ref = useRef<THREE.Mesh>(null!);
  const start = useMemo(() => new THREE.Vector3(...source), [source]);
  const end = useMemo(() => new THREE.Vector3(...target), [target]);
  const temp = useMemo(() => new THREE.Vector3(), []);

  useFrame(({ clock }) => {
    const t = (Math.sin((clock.elapsedTime / duration) * Math.PI * 2) + 1) / 2;
    temp.lerpVectors(start, end, t);
    ref.current.position.copy(temp);
  });

  return (
    <mesh ref={ref}>
      <sphereGeometry args={[0.04, 16, 16]} />
      <meshStandardMaterial transparent opacity={0.45} />
    </mesh>
  );
}

function Scene() {
  return (
    <>
      <ambientLight intensity={1.2} />
      <directionalLight position={[3, 4, 5]} intensity={1.2} />
      <gridHelper args={[10, 10]} />
      <axesHelper args={[2]} />

      {/* 0D point */}
      <Primitive kind="point" position={[-2, 0.2, 0]} />

      {/* 1D line shown as a thin rod */}
      <Primitive kind="line" position={[0, 0.5, 0]} rotation={[0, 0, Math.PI / 2]} length={2} />

      {/* 2D plane */}
      <Primitive kind="plane" position={[2, 0.5, 0]} size={1.5} />

      {/* Simple emanation sweep preview */}
      <SweepGhost source={[-2, 0.2, 0]} target={[-0.5, 1.2, 0]} duration={3} />
      <SweepGhost source={[0, 0.5, 0]} target={[0, 0.5, 1.5]} duration={4} />
      <SweepGhost source={[2, 0.5, 0]} target={[2, 0.5, 1.2]} duration={5} />
    </>
  );
}

export default function GeometryStage() {
  return (
    <Canvas camera={{ position: [0, 2, 6], fov: 50 }}>
      <Scene />
    </Canvas>
  );
}
```

### Python `GeometricPrimitive` class and residue lookup

SciPy/SymPy/trimesh/PyBullet belong around this core, but the first working version should keep the semantic layer simple and deterministic. citeturn56view0turn56view1turn57view0turn57view3

```python
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Dict, Optional


@dataclass
class PrimitiveProfile:
    motion_type: str
    tracking_geometry: str
    problem_envelope: str
    residue_filter: str


@dataclass
class GeometricPrimitive:
    name: str
    dimensions: int
    profiles: Dict[str, PrimitiveProfile] = field(default_factory=dict)

    def add_profile(
        self,
        profile_name: str,
        motion_type: str,
        tracking_geometry: str,
        problem_envelope: str,
        residue_filter: str,
    ) -> None:
        self.profiles[profile_name] = PrimitiveProfile(
            motion_type=motion_type,
            tracking_geometry=tracking_geometry,
            problem_envelope=problem_envelope,
            residue_filter=residue_filter,
        )


class PrimitiveLibrary:
    def __init__(self) -> None:
        self._library: Dict[str, GeometricPrimitive] = {}

    def register(self, primitive: GeometricPrimitive) -> None:
        self._library[primitive.name] = primitive

    def residue_lookup(self, failure_mode: str) -> Optional[dict]:
        for primitive in self._library.values():
            for profile_name, profile in primitive.profiles.items():
                if profile.problem_envelope == failure_mode:
                    return {
                        "source_primitive": primitive.name,
                        "failed_profile": profile_name,
                        "motion_type": profile.motion_type,
                        "tracking_geometry": profile.tracking_geometry,
                        "required_residue_key": profile.residue_filter,
                    }
        return None


def build_default_library() -> PrimitiveLibrary:
    library = PrimitiveLibrary()

    line = GeometricPrimitive(name="1D_Line", dimensions=1)
    line.add_profile(
        profile_name="Axial_Spindle_Spin",
        motion_type="Rotation",
        tracking_geometry="Null_Spatial_Volume",
        problem_envelope="Conical_Wobble_Deflection",
        residue_filter="Hollow_Conical_Bearing_Cap",
    )
    library.register(line)

    plane = GeometricPrimitive(name="2D_Plane", dimensions=2)
    plane.add_profile(
        profile_name="Flat_Peripheral_Spin",
        motion_type="Rotation",
        tracking_geometry="Static_2D_Disk",
        problem_envelope="Surface_Friction_Slippage",
        residue_filter="Interference_Teeth_Grooves",
    )
    library.register(plane)

    point = GeometricPrimitive(name="0D_Point", dimensions=0)
    point.add_profile(
        profile_name="Coordinate_Anchor",
        motion_type="Translation",
        tracking_geometry="Line_Segment",
        problem_envelope="Translational_Drift",
        residue_filter="Socket_Anchor_Constraint",
    )
    library.register(point)

    return library


if __name__ == "__main__":
    lib = build_default_library()
    result = lib.residue_lookup("Conical_Wobble_Deflection")
    print(result)
```

### Chat parser pseudocode to spawn visualizations

The parser should produce **candidate interpretations**, not one brittle parse.

```text
function parsePromptToScene(prompt):
    tokens = normalize(prompt)
    entities = []

    geometryLexicon = {
        "point": Primitive("0D_Point"),
        "dot": Primitive("0D_Point"),
        "line": Primitive("1D_Line"),
        "plane": Primitive("2D_Plane"),
        "circle": Primitive("Circle"),
        "sphere": Primitive("Sphere"),
        "triangle": Primitive("Triangle"),
        "tetrahedron": Primitive("Tetrahedron"),
        "cube": Primitive("Cube"),
        "spiral": Primitive("Spiral"),
        "arc": Primitive("Arc")
    }

    profileLexicon = {
        "spin": Profile("Axial_Spindle_Spin"),
        "hinge": Profile("Out_of_Plane_Hinge"),
        "drift": ProblemEnvelope("Translational_Drift"),
        "wobble": ProblemEnvelope("Conical_Wobble_Deflection"),
        "slip": ProblemEnvelope("Surface_Friction_Slippage")
    }

    for tokenWindow in slidingWindows(tokens):
        if tokenWindow matches geometryLexicon:
            entities.append(makePrimitiveNode(tokenWindow))
        if tokenWindow matches profileLexicon:
            entities.append(makeProfileOrFailureNode(tokenWindow))

    relations = inferRelations(entities, prompt)
        - if "made of", "composed of", "combination of" => CONVERGES_INTO
        - if "fails", "wobbles", "slips" => FAILS_AS
        - if "fix", "stabilize", "fit", "cap", "groove" => INVERTS_TO / STABILIZED_BY

    scenePreset = chooseScenePreset(entities, relations)
        - atomic_primitives
        - sweep_demo
        - failure_overlay
        - residue_fit
        - invention_composite

    return {
        "nodes": entities,
        "edges": relations,
        "scenePreset": scenePreset,
        "inspectorFocus": highestConfidenceEntity(entities),
        "clarificationCandidates": ambiguousTerms(entities)
    }
```
